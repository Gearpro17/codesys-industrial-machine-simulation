# I/O Map — Industrial Process Control & Monitoring System

## 1. Architecture

```text
+----------------------+        Modbus TCP        +----------------------+
|      C++ Plant       | <----------------------> |   CODESYS PLC        |
|      Simulator       |                          |   Controller         |
|----------------------|                          |----------------------|
| Sensors              |                          | State machine        |
| Actuators             |                          | Safety/interlocks     |
| Physical simulation   |                          | Recipes              |
| PID control           |                          | Sequencing            |
| Fault injection       |                          | PLC diagnostics       |
+----------+-----------+                          +----------+-----------+
           |                                                 |
           | TCP/HTTP                                        |
           v                                                 |
+----------------------+                          +----------------------+
|   SQLite Historian   | <------------------------ |     C# SCADA/HMI     |
|----------------------|                          |----------------------|
| Measurements         |                          | Machine state        |
| Alarms               |                          | Alarms               |
| Events               |                          | Trends               |
| Production runs      |                          | Production KPIs      |
+----------------------+                          +----------------------+
```

The CODESYS PLC owns the machine sequence and automation logic. The C++ application simulates the physical plant, sensors, actuators, control algorithms, asynchronous acquisition and faults. The C# application provides the SCADA/HMI layer, while SQLite stores historical measurements, alarms and production data.

## 2. Plant → PLC

These signals are generated by the C++ plant simulator and exposed to the CODESYS PLC through Modbus TCP.

| Signal | Type | Modbus Address | Notes |
|---|---|---:|---|
| `startButton` | BOOL | DI 0 | Start command |
| `stopButton` | BOOL | DI 1 | Normally closed in a real installation; `FALSE` represents an activated/open stop circuit |
| `emergencyStop` | BOOL | DI 2 | Normally closed wiring; `TRUE` = healthy/released, `FALSE` = pressed/open |
| `entrySensor` | BOOL | DI 3 | Detects a box entering the line |
| `inspectionSensor` | BOOL | DI 4 | Indicates that a box is positioned at the inspection station |
| `palletPresent` | BOOL | DI 5 | Detects an available pallet |
| `stackerUpLimit` | BOOL | DI 6 | Stacker upper limit switch |
| `stackerDownLimit` | BOOL | DI 7 | Stacker lower limit switch |
| `gripperClosedFb` | BOOL | DI 8 | Gripper closed feedback |
| `palletFull` | BOOL | DI 9 | Pallet-full indication; alternatively calculated by PLC counter |
| `boxHeight` | INT | IR 0 | Height scaled in 0.1 mm |
| `conveyorSpeedFb` | INT | IR 1 | Conveyor speed feedback in mm/s |
| `temperature` | INT | IR 2 | Temperature scaled in 0.1 °C |
| `pressure` | INT | IR 3 | Pressure scaled in 0.01 bar |

### 2.1 Scaling

Modbus registers are represented as integers, so engineering values are transmitted using explicit scaling factors.

Examples:

```text
boxHeight = 1500  → 150.0 mm

temperature = 235 → 23.5 °C

pressure = 725 → 7.25 bar
```

The scaling factor must be documented on both sides of the communication interface.

These signals are generated by CODESYS and consumed by the C++ plant simulator.

| Signal | Type | Modbus Address | Notes |
|---|---|---:|---|
| `conveyorMotor` | BOOL | Coil 0 | Conveyor motor command |
| `rejectCylinder` | BOOL | Coil 1 | Activates reject mechanism |

| `stackerDown` | BOOL | Coil 3 | Commands stacker downward |
| `gripperClose` | BOOL | Coil 4 | Commands gripper to close |
| `speedSetpoint` | INT | HR 0 | Conveyor speed command in mm/s |

| `activeRecipeId` | INT | HR 2 | Active box/product recipe |
| `heartbeat` | INT | HR 3 | PLC communication watchdog counter |

## 4. PLC State Encoding

The `plcState` holding register uses the following integer mapping:

| Value | State |
|---:|---|
| 0 | `STOPPED` |
| 1 | `STARTING` |
| 2 | `RUNNING` |
| 3 | `INSPECTION` |
| 4 | `REJECTING` |
| 5 | `TRANSFERRING` |
| 6 | `STACKING` |
| 7 | `PALLET_FULL` |
| 8 | `PALLET_CHANGE` |
| 9 | `FAULT` |
| 10 | `EMERGENCY_STOP` |

The corresponding C++ representation can be:

```cpp
enum class PLCState {
    STOPPED = 0,
    STARTING = 1,
    RUNNING = 2,
    INSPECTION = 3,
    REJECTING = 4,
    TRANSFERRING = 5,
    STACKING = 6,
    PALLET_FULL = 7,
    PALLET_CHANGE = 8,
    FAULT = 9,
    EMERGENCY_STOP = 10
};
```

Keeping the numeric mapping identical between CODESYS, C++ and the SCADA layer avoids ambiguous state interpretation.

## 5. Recipe Example

The PLC selects the active recipe using `activeRecipeId`.

| Recipe ID | Product Type | Expected Height |
|---:|---|---:|
| 1 | Type A | 100 mm |
| 2 | Type B | 150 mm |
| 3 | Type C | 200 mm |

The inspection sequence compares `boxHeight` against the expected height of the active recipe. A box outside the configured tolerance is rejected.

Example:

```text
Recipe: Type B
Expected height: 150 mm
Tolerance: ±5 mm

Measured: 152 mm → ACCEPT
Measured: 158 mm → REJECT
```

The tolerance itself can be stored as part of the recipe configuration.

## 6. Emergency Stop Convention

The emergency-stop input represents a fail-safe normally closed circuit:

```text
TRUE  → safety circuit healthy / E-stop released
FALSE → circuit open / E-stop pressed or faulted
```

When `emergencyStop == FALSE`, the PLC must transition to `EMERGENCY_STOP` and remove machine motion commands according to the simulated safety design.

> **Important:** This software project demonstrates the control concept only. The simulated emergency-stop mechanism is **not a certified safety system** and must not be treated as a substitute for real safety-rated hardware, safety PLCs or safety relays.

This is also a useful interview point: in industrial automation, emergency-stop circuits are commonly designed so that a broken wire or loss of continuity results in the safe state.

---

## 7. Stop Button Convention

The normal stop button is also represented as a normally closed circuit:

```text
TRUE  → stop circuit healthy
FALSE → stop command / circuit open
```

The PLC should distinguish a normal stop from an emergency stop. A normal stop can perform a controlled shutdown, while an emergency stop immediately moves the machine into the emergency state according to the safety architecture.

## 8. Heartbeat / Communication Supervision

The PLC increments `heartbeat` periodically. The C++ plant simulator monitors the value and detects whether the PLC is still communicating.

Example concept:

```text
PLC heartbeat:
0 → 1 → 2 → 3 → 4 → ...
```

If the value does not change within a configured timeout, the plant simulator can declare a communication fault and place the simulated plant in a safe state.

The heartbeat is intended for **communication supervision**, not functional safety certification.

## 9. Conveyor Motor Fault Detection

The C++ simulator can compare the commanded conveyor speed against the simulated feedback.

Example logic:

```text
IF conveyorMotor = TRUE
AND speedSetpoint > minimumSpeed
AND conveyorSpeedFb < minimumFeedback
FOR longer than faultTimeout
THEN
    raise ConveyorMotorFault
```

This allows the project to demonstrate a realistic automation diagnostic without requiring physical hardware.

## 11. C++ Cyclic Runtime

The C++ simulator should operate around a deterministic simulation cycle. A target of approximately 10 ms is suitable for this portfolio project, while making clear that this is **not a hard real-time guarantee**.

Conceptually:

```cpp
while (running) {
    readInputs();
    executeControlLogic();
    updatePlant();
    updateOutputs();
    measureCycleTime();
    waitUntilNextCycle();
}
```

The project can use modern C++ facilities such as:

- `std::chrono` for timing
- `std::thread` for concurrent tasks
- `std::mutex` and `std::lock_guard` for shared data protection
- `std::condition_variable` for producer/consumer synchronization
- `std::atomic` for simple thread-safe state
- RAII and smart pointers for resource management
- STL containers and algorithms

## 12. PID Control

The C++ runtime can include a PID controller for a simulated process variable such as conveyor speed, temperature or pressure.

A basic PID controller follows:

```text
u(t) = Kp * e(t)
     + Ki * integral(e(t))
     + Kd * derivative(e(t))
```

The implementation should account for:

- Sampling time (`dt`)
- Output saturation
- Integral wind-up
- Derivative calculation
- Configurable `Kp`, `Ki` and `Kd`

For the conveyor, for example, the PLC can provide `speedSetpoint`, while the C++ plant simulates motor dynamics and returns `conveyorSpeedFb`.

- Active recipe

## 15. Responsibility Boundaries

### CODESYS PLC

Responsible for:

- Main automation sequence
- State machine
- Interlocks
- Recipe selection
- Box inspection decision
- Reject sequencing
- Stacker sequencing
- Pallet handling
- Normal start/stop behavior
- Emergency-state handling
- PLC diagnostics

### C++ Plant Simulator

Responsible for:

- Physical process simulation
- Sensor simulation
- Actuator response
- Motor/process dynamics
- PID implementation
- Cyclic runtime
- Asynchronous sensor acquisition
- Fault injection
- Communication supervision

### C# SCADA/HMI

Responsible for:

- Operator visualization
- Trends
- Alarms
- Events
- Production information
- Machine status

### SQLite

Responsible for:

- Measurements
- Alarm history
- Event history
- Production history

This separation keeps the project representative of an industrial automation architecture while preventing the individual components from duplicating each other's responsibilities.
